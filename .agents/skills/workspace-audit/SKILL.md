# Workspace Audit

## Purpose

Проверяй минимальную достаточность контекста для полезной работы AI с уже заявленными целями пользователя. Все пути указаны относительно корня репозитория.

Не оптимизируй Workspace на полноту. Оптимизируй его на полезность.

Хороший Workspace может быть маленьким.

Считай проблемой только то, что соответствует хотя бы одному критерию:

- отсутствующая информация мешает учитывать уже заявленные цели пользователя;
- из-за отсутствующей информации AI с высокой вероятностью будет давать существенно менее точные ответы в текущих задачах;
- существующие данные противоречат друг другу;
- важная информация явно устарела;
- структура содержит ненужное дублирование или мусор.

Для отсутствующих данных укажи конкретную текущую задачу и последствие их отсутствия. Возможность добавить сведения сама по себе не является проблемой. Не придумывай пользователю дополнительные цели и не делай предположений о том, какую информацию он обязан хранить.

## Workflow

### Step 1 — Inspect workspace

Проверь существующие файлы в `context/`, `decisions/` и `references/`. Используй релевантный контекст разговора. Не рассматривай `*.example.md` как пользовательские данные — это только шаблоны.

Отсутствие персонального файла или незаполненное поле не означает проблему. Оценивай практические последствия, а не заполненность директорий.

### Step 2 — Evaluate context quality

Оценивай прежде всего:

- понятно ли, чем пользователь занимается;
- понятны ли его текущие приоритеты;
- достаточно ли информации, чтобы учитывать его рабочий контекст;
- есть ли противоречия;
- есть ли явно устаревшая информация;
- есть ли ненужные дубли или мусор.

Не стремись заполнить каждое возможное поле. Context может иметь статус Good при незаполненных деталях, если информации достаточно для текущей работы.

Не считай автоматически пробелами точную целевую должность, размер аудитории, платформу блога, уровень владения каждым инструментом, недельный бюджет времени, подробную биографию или дополнительные business-поля. Рекомендуй их уточнение только при наличии обозначенной пользователем задачи, для которой они действительно необходимы. Общая цель сама по себе не делает все детали её будущего плана обязательными для постоянного хранения.

Не придумывай отсутствующую информацию. Отличай подтверждённые проблемы от предположений. Не объявляй данные устаревшими только из-за возраста файла: укажи основание. Не превращай непроверенную актуальность в проблему без конкретной причины для сомнения.

### Step 3 — Evaluate decisions

Отсутствие `decisions/log.md` само по себе не является проблемой. Если решения ещё не накопились, используй Not needed yet. Не предлагай создавать журнал на всякий случай.

Считай отсутствие истории решений проблемой только если из контекста видно, что важные долгосрочные решения уже принимаются, нигде не фиксируются и из-за этого может теряться логика работы. Укажи конкретное решение и риск потери его обоснования.

Если журнал существует, проверь причины важных решений, понятность их статуса и противоречия текущим целям или рабочему контексту. Явно отменённое решение может быть полезной историей; проблема возникает, если его статус или влияние на текущую работу неясны.

### Step 4 — Evaluate references

Проверь практическую пользу существующих материалов, явное устаревание и ненужное дублирование контекста.

Отсутствие пользовательских reference-файлов не является автоматической проблемой. Если пользователь нормально работает без них, используй Not configured; этот статус не означает, что требуется действие.

Рекомендуй reference-файл только при очевидной пользе для существующей работы. Например, voice samples могут помочь при регулярном написании контента, product reference — при работе с конкретным продуктом, SOP — при регулярно повторяемом процессе. Это примеры, а не обязательный набор.

Если пользователь сознательно отказался от voice samples во время onboarding, не помечай это как проблему и не повторяй рекомендацию без новой практической необходимости. Не предлагай материалы ради заполнения директории.

### Step 5 — Produce audit report

Покажи короткий отчёт прямо в ответе, без создания файла отчёта. Используй следующую структуру и допустимые статусы:

## Workspace Health

- Context: Good / Needs attention / Missing
- Decisions: Good / Needs attention / Not needed yet
- References: Good / Needs attention / Not configured

Выбери один статус для каждой категории и добавь одно короткое обоснование:

- Good — материалов достаточно для текущей работы, существенных проблем нет.
- Needs attention — есть конкретная проблема, соответствующая критериям Purpose.
- Missing — содержательный персональный контекст отсутствует; поясни, мешает ли это текущим задачам. Сам статус не требует заполнения Workspace.
- Not needed yet — история решений пока не нужна.
- Not configured — пользовательских reference-материалов пока нет и подтверждённой проблемы из-за этого не обнаружено.

## Issues Found

Показывай только реальные проблемы с указанием файлов и разделов, если они существуют, и кратким описанием последствий. Не включай гипотетические пробелы и лишние персональные данные. Если проблем нет, напиши: «Проблем не найдено».

## Recommended Actions

### High Priority

Только проблемы, которые прямо сейчас реально мешают AI использовать Workspace. Если их нет, напиши: «Критичных проблем не найдено.»

### Medium Priority

Только улучшения с понятной связью с текущими целями пользователя. Для каждой рекомендации объясни: «Это поможет X, потому что Y». Не рекомендуй дополнительные данные без конкретной пользы.

### Optional

Максимум 3 действительно необязательных улучшения с понятной практической пользой. Не перечисляй всё, что теоретически можно добавить.

Не придумывай рекомендации ради заполнения категорий. Если для Medium Priority или Optional нет действий, кратко укажи это.

### Step 6 — No automatic edits

Этот skill является диагностическим. Не изменяй файлы автоматически.

Если пользователь хочет применить рекомендации, предложи использовать `update-context` для персональных файлов `context/` или явно подтвердить конкретные изменения. До такого подтверждения ограничься отчётом и предложениями.

Не изменяй `AGENTS.md`, `*.example.md` или другие skills. Не создавай reference-файлы и не изменяй decision log автоматически. Не делай `git commit` или `git push`.
